# 页面到模型映射推导 V1 联合评审

项目：info-organization-product  
评审对象：`docs/04-domain/page-to-model-mapping-v1.md`

---

# 1. 评审目标

验证页面到模型的映射推导是否：
1. 支撑前台页面任务
2. 支撑页面展示需求
3. 模型边界合理
4. 守住方法论主链

---

# 2. 产品经理评审

## 结论
**通过，92 分**

## 优点
### A. 映射推导清晰
每个页面的核心动作都有明确对应：
- 收集页 → Entry 创建
- 待处理页 → 读模型带 currentSuggestedAction
- 查找页 → SearchResultItem
- 专题页 → TopicDetailView
- 详情页 → EntryDetailView

### B. "当前建议动作"设计正确
待处理页最关键的是：系统告诉用户该做什么。  
currentSuggestedAction 这个字段直接解决了这个问题。

### C. 读写分离合理
页面展示用的数据和操作用的数据分开了，这避免前台被迫自己拼状态。

## 保留意见
### 问题 1：跳过后的再出现规则还不够细
文档里说"经过一定时间窗口可重新回到前部"，但没说具体多久。  
建议：下一步状态流设计时明确时间窗口参数。

---

# 3. UI/交互评审

## 结论
**通过，90 分**

## 优点
### A. 读模型字段符合页面需求
- RecentEntryItem 只要预览，不要全文 ✅
- PendingEntryItem 有建议动作 ✅
- SearchResultItem 有命中片段 ✅
- TopicDetailView 有条目数 ✅

### B. 没有让前台自己判断状态
currentSuggestedAction 由后端推导，前台只渲染，这是对的。

## 保留意见
### 问题 1：SearchResultItem 的 contentSnippet 需要明确长度
建议：下一步 API 设计时明确片段长度（如前后各 50 字）。

### 问题 2：TopicDetailView 的 entries 需要分页
如果专题内条目很多，一次性返回会炸。  
建议：下一步 API 设计时加分页参数。

---

# 4. 架构师评审

## 结论
**通过，94 分**

## 优点
### A. 写模型边界清晰
- Entry 是核心聚合根
- Topic 是独立聚合根
- ReuseRecord 是轻量行为记录

### B. 读写分离正确
写模型和读模型分开，避免了"万能 DTO"陷阱。

### C. 首版克制
- Insight 作为字段，不独立成表 ✅
- Topic 只允许一个主归属 ✅
- ReuseRecord 只记录复制，不做输出系统 ✅

## 保留意见
### 问题 1：Entry.skippedAt 的索引要注意
待处理流查询时会用到 skippedAt，需要加索引。

### 问题 2：读模型的实现方式要在下一步明确
是视图、是查询投影、还是缓存？  
建议：下一步查询模型设计时明确。

# 5. 奥野宣之监督人评审

## 结论
**通过，95 分**

## 守住了什么
### 1. 先收进来
Entry 创建时只需要 rawContent，其他都可空。  
✅ 符合"先收进来，比先管理更重要"

### 2. 附着思考
insightText 作为 Entry 的核心字段存在。  
✅ 符合"没有自己的理解，信息就还不是自己的"

### 3. 归入持续问题
Topic 作为独立对象存在，不是标签。  
✅ 符合"持续问题需要稳定上下文"

### 4. 直接取用
ReuseRecord 记录复制行为。  
✅ 符合"整理是为了未来拿出来用"

### 5. 不逼用户经营
跳过只是标记，不是删除。  
待处理流由系统推导建议动作。  
✅ 符合"好的系统不是要求用户经营"

## 正向意见
这份映射推导最大的价值在于：

> 它把方法论主链翻译成了数据结构，而不是只停留在页面交互层。

这说明产品设计已经从"UI 正确"进入"模型也正确"的阶段。
