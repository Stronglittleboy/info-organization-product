# 文档治理补丁 V1

项目：info-organization-product  
路径：/vol3/1000/private/workProject/info-organization-product

---

# 1. 目的

为项目建立稳定、可持续维护的文档治理规范，解决以下问题：
1. 文档目录再次平铺失控
2. 工作稿与正式稿混淆
3. 评审记录、设计稿、实施稿写入位置不统一
4. 版本升级后旧稿没有正确归档

本补丁生效后，后续所有新增文档必须遵守本规范。

---

# 2. 文档分层原则

项目文档分为两层：

## 2.1 正式文档层（docs/）
用于沉淀：
- 可被后续阶段引用的正式版本
- 已经过评审或准备用于评审的主文档
- 能代表当前项目阶段共识的文档

特点：
- 结构化
- 稳定
- 可索引
- 可作为后续输入

## 2.2 工作过程层（reviews/、tasks/、notes/）
用于记录：
- 原始评审记录
- 任务推进状态
- 临时过程笔记
- 阶段性摘要

特点：
- 可临时
- 可快速记录
- 不要求最终呈现质量
- 后续可选择镜像或沉淀进 docs/

# 3. 正式文档目录规范

## 3.1 docs/00-overview
放：
- 项目索引
- 当前阶段状态
- 项目路线图
- 文档治理规则

禁止放：
- 具体页面设计稿
- API 细节
- 临时会议纪要

## 3.2 docs/01-research
放：
- 方法论来源
- 作者监督人角色说明
- 竞品/理论/背景研究

禁止放：
- 页面交互定稿
- 研发任务单

## 3.3 docs/02-product
放：
- 产品定义
- 用户画像
- 版本范围
- 业务目标
- 产品约束

禁止放：
- 具体接口字段
- 页面组件细节

## 3.4 docs/03-design
放：
- 页面职责
- 低保真
- 中保真
- 高保真（未来）
- 交互规则

禁止放：
- 后端模型定义
- API 返回示例

## 3.5 docs/04-domain
放：
- 领域模型
- 状态流
- 查询模型
- 聚合边界

禁止放：
- 具体 UI 布局
- 临时任务安排

## 3.6 docs/05-api
放：
- API 草案
- 读写模型映射
- 接口契约
- 错误码/状态码规则（后续）

禁止放：
- 页面视觉稿

## 3.7 docs/06-reviews
放：
- 已沉淀的正式评审结论
- 设计评审摘要
- 实施设计评审摘要

禁止放：
- 未整理的原始长对话
- 临时评语草稿

## 3.8 docs/99-archive
放：
- 被替换旧版
- 回滚文档
- 废弃草稿

规则：
- 归档文档必须保留版本号
- 不得把当前有效主文档放入 archive

# 4. 工作过程层目录规范

## 4.1 reviews/
定位：原始评审记录仓

放：
- 原始多角色评审稿
- 未压缩的评审过程
- 讨论纪要原文

与 docs/06-reviews 的关系：
- reviews/ 保留原始过程
- docs/06-reviews 保留正式沉淀版

## 4.2 tasks/
定位：任务推进仓

放：
- 当前阶段任务状态
- 里程碑任务拆解
- 待办与阻塞

禁止放：
- 正式产品设计稿
- 接口契约正文

## 4.3 notes/
定位：过程笔记仓

放：
- 临时分析
- 阶段小结
- 未定案想法
- 补充说明

规则：
- notes 不是正式引用源
- 若笔记升格，应复制/整理进入 docs/

# 5. 命名规范

## 5.1 正式主文档命名
格式：
`主题名-v版本号.md`

示例：
- `mid-fidelity-interaction-v1.1.md`
- `domain-model-v1.md`
- `state-flow-v1.md`

## 5.2 概览/索引类文档命名
可不强制版本号：
- `project-index.md`
- `project-status.md`
- `product-definition.md`

## 5.3 评审文档命名
格式：
`对象-review-v版本号.md`
或
`对象-review-with-角色名.md`

示例：
- `mid-fidelity-review-v1.1.md`
- `low-fidelity-review-with-okuno.md`

## 5.4 归档文档命名
必须保留原版本号，不可改写成模糊名称。

# 6. 版本治理规则

## 6.1 何时升级版本
满足以下任一条件时应升级版本：
1. 页面结构发生实质变化
2. 领域对象边界发生变化
3. 评审后结论发生改判
4. 文档不只是润色，而是逻辑更新

## 6.2 何时覆盖原文档
仅当以下情况允许覆盖：
1. 错别字修正
2. 小范围表达优化
3. 不改变结构和结论的微调

## 6.3 何时归档旧版
升级主版本或次版本时：
- 旧版移入 `docs/99-archive/`
- 新版写回对应正式目录

---

# 7. 写入规则

## 7.1 新文档写入前必须先判断层级
任何新文档写入前，必须先回答：
1. 这是正式文档，还是过程文档？
2. 它属于产品、设计、领域、API、评审中的哪一层？
3. 它是否会成为后续阶段的输入？

## 7.2 默认写入策略
- 正式共识类文档 -> `docs/`
- 原始评审过程 -> `reviews/`
- 阶段任务推进 -> `tasks/`
- 临时想法与笔记 -> `notes/`

## 7.3 禁止事项
- 禁止把正式设计稿直接写到 notes/
- 禁止把原始评审长文直接放进 docs/03-design
- 禁止把未定稿接口直接写成最终契约
- 禁止版本升级时无归档覆盖旧版

---

# 8. 当前项目的具体执行规则

对于本项目，后续默认按以下策略：

## 正式文档
一律优先写入 `docs/` 对应分层目录。

## 评审
- 原始稿 -> `reviews/`
- 沉淀稿 -> `docs/06-reviews/`

## 任务
- 任务状态、实施前后阶段推进 -> `tasks/`

## 笔记
- 临时过程性分析 -> `notes/`

## 归档
- 被替换版本 -> `docs/99-archive/`

---

# 9. 当前生效结论

从本补丁生效后：
1. docs/ 成为唯一正式文档树
2. reviews/tasks/notes 仅作为工作过程层
3. 所有新版本文档必须遵守版本与归档规则
4. 后续写入前，先判断层级，再决定目录

---

# 10. 下一步影响

本补丁生效后，后续继续推进 API 草案、查询模型、研发任务拆解时，文档将按以下固定位置写入：
- API 草案 -> `docs/05-api/`
- 查询模型 -> `docs/04-domain/`
- 正式评审 -> `docs/06-reviews/`
- 原始评审过程 -> `reviews/`
- 研发任务拆解 -> `tasks/`

这将作为后续所有写入动作的默认规则。
